# Этап 5. Надёжность VidSec

## Что сделано

| Компонент | Как защищён от отказа | Переключение | Проверено |
|---|---|---|---|
| PostgreSQL `video-db` | primary + standby, потоковая репликация; сторож `failover` продвигает standby в master | автоматически, ≈7 с | `docker compose kill video-db`: 2 неуспешных запроса, дальше всё работает |
| RabbitMQ | кластер из 3 узлов, очередь `video.processing` типа quorum (копия на каждом узле, запись подтверждается большинством) | автоматически, клиенты переходят на следующий узел | `docker compose kill rabbitmq`: автотест 32/32, видео обработано через rabbitmq-2 |
| Данные обеих БД | `pg_dump` раз в час, хранятся 24 копии в папке `backups/` | восстановление одной командой | удалили все видео, восстановили за 0,3 с |
| Остальные сервисы | `restart: unless-stopped`, api и worker переподключаются сами | перезапуск Docker, 2–10 с | |

## Как это работает

**PostgreSQL.** Standby при первом старте копирует данные с primary (`pg_basebackup`) и дальше
получает журнал изменений (WAL) в реальном времени. Сторож `failover` каждые 2 с проверяет оба узла.
Если primary не отвечает 3 проверки подряд, сторож выполняет на standby `SELECT pg_promote()`.
api, video-worker и backup подключаются строкой
`host=video-db,video-db-standby target_session_attrs=read-write`: драйвер libpq сам находит узел,
который принимает запись. Если старый primary после аварии поднимается снова, сторож переводит его
в режим только чтения, чтобы не получилось двух master (split-brain).

**RabbitMQ.** Три узла с общим Erlang cookie находят друг друга по списку в `rabbitmq/cluster.conf`.
Quorum-очередь построена на алгоритме Raft: у неё есть лидер и две реплики, сообщение считается
принятым, когда его записало большинство (2 из 3). api публикует с подтверждением (`confirm_delivery`),
воркер подтверждает задачу (`ack`) только после обработки. При падении узла выбирается новый лидер,
клиенты переподключаются к следующему узлу из списка.

**Резервные копии.** Контейнер `backup` раз в `BACKUP_INTERVAL` секунд (по умолчанию час) делает
`pg_dump -Fc` обеих баз и удаляет копии старше 24 последних.

## Параметры обслуживания

### SLO (цели уровня обслуживания)

| SLI (что меряем) | SLO (цель) | Бюджет ошибок |
|---|---|---|
| Доля успешных ответов (не 5xx) на запросы к `/api/*` и `/auth/*` за месяц | 99,5 % | 0,5 % ≈ 3 ч 36 мин в месяц |
| Время ответа API без загрузки и отдачи видео | 95 % запросов быстрее 500 мс | 5 % медленных |
| Время обработки загруженного видео | 99 % видео готовы за 2 мин | 1 % |

Почему 99,5 %, а не 99,99 %. Отказ базы видео или узла брокера теперь стоит секунды, но вся система
по-прежнему работает на одном хосте Docker: ноутбук, одна виртуальная машина Docker Desktop, один
экземпляр nginx, api, Redis и хранилища S3. Перезагрузка хоста занимает около 5 минут. Закладываем
до 4 перезагрузок в месяц (обновления ОС и Docker), это 20 минут. Плюс перезапуски одиночных
сервисов и развёртывание новых версий. 99,5 % оставляет запас и честно отражает единую точку отказа.
Для учебного видеохостинга без платных клиентов это разумный уровень: такой SLO у многих
внутренних сервисов.

### MTBF и MTTR

MTBF (среднее время между отказами) взято из оценки, а не из статистики: у учебного проекта нет
истории инцидентов. MTTR (среднее время восстановления) измерено на демонстрационных отказах.

| Компонент | MTBF, оценка | MTTR | Откуда MTTR |
|---|---|---|---|
| Один узел PostgreSQL | 720 ч (30 дней) | 7–10 с | измерено: 6 с на обнаружение + 1,4 с на promote |
| Пара PostgreSQL primary + standby | ≈ 260 000 ч | — | расчёт ниже |
| Один узел RabbitMQ | 720 ч | < 5 с | измерено: переподключение клиента к следующему узлу |
| Redis (кеш, один экземпляр) | 720 ч | 2–5 с | перезапуск Docker; теряются просмотры за последние ≤ 30 с |
| api, auth-service, video-worker, nginx | 720 ч | 2–5 с | перезапуск Docker |
| Хост Docker целиком | 180 ч (4 раза в месяц) | 5 мин | перезагрузка ноутбука и запуск контейнеров |
| Порча данных (ошибка, удаление) | — | ≈ 5 мин | восстановление из копии + время человека на решение |

Почему 720 часов. Это порядок частоты, с которой процесс в контейнере падает или перезапускается
из-за обновлений образов, нехватки памяти и сбоев хоста в небольших инсталляциях: примерно раз в месяц.

Пара узлов PostgreSQL недоступна, только если второй узел откажет, пока первый ещё не восстановлен.
Время восстановления узла (пересоздать standby) берём T = 1 ч:

MTBF пары ≈ MTBF² / (2 · T) = 720² / (2 · 1) ≈ 259 200 ч ≈ 30 лет.

Доступность одного компонента: A = MTBF / (MTBF + MTTR).
Для узла PostgreSQL с автопереключением: A = 720 ч / (720 ч + 10 с) ≈ 99,9996 %.
Для хоста Docker: A = 180 / (180 + 0,083) ≈ 99,95 %. Хост и задаёт потолок всей системы.

### RPO и RTO

| Сценарий | RPO (сколько данных можно потерять) | RTO (за сколько восстановиться) |
|---|---|---|
| Падение primary PostgreSQL | отставание репликации: измерено 0–80 байт, < 1 с (асинхронная) | ≈ 10 с, автоматически |
| Падение узла RabbitMQ | 0 для подтверждённых сообщений (quorum) | < 5 с, автоматически |
| Падение Redis | счётчики просмотров за ≤ 30 с; кеш пересчитывается | ≤ 5 с |
| Порча или удаление данных в БД | ≤ 1 ч (интервал копий) | ≤ 15 мин, вручную |

## Демонстрация на защите

```bash
# 0. Состояние кластеров
docker compose exec failover python watcher.py status
docker compose exec rabbitmq-2 rabbitmqctl cluster_status

# 1. Отказ master PostgreSQL
docker compose kill video-db                   # аварийно «роняем» master
docker compose logs -f failover                # через ≈6 с: "video-db-standby стал master"
docker compose exec failover python watcher.py status    # video-db down, standby primary
# сайт работает: открыть страницу, поставить лайк, загрузить видео
docker compose start video-db                  # старый master вернулся
docker compose logs --tail 3 failover          # "перевожу его в режим только чтения (split-brain)"

# 2. Отказ узла RabbitMQ
docker compose exec rabbitmq-2 rabbitmq-queues quorum_status video.processing   # кто лидер
docker compose kill rabbitmq
docker compose logs --tail 3 video-worker      # "Подключён к RabbitMQ (узел rabbitmq-2)"
# загрузить видео — оно обработается
docker compose start rabbitmq                  # узел вернётся в кластер и догонит очередь

# 3. Резервная копия и восстановление
docker compose exec backup sh /scripts/backup.sh               # сделать копию сейчас
docker compose exec backup sh /scripts/restore.sh              # список копий
docker compose exec video-db-standby psql -U video_service -d videos -c "SELECT count(*) FROM videos"
# удалить видео в браузере (или DELETE в psql на текущем master)
docker compose exec backup sh /scripts/restore.sh latest       # восстановить последнюю копию
```

`psql` на standby работает только на чтение. Писать можно на тот узел, который сейчас master
(`watcher.py status`).

### Вернуть исходные роли после переключения

После переключения master — это `video-db-standby`, а `video-db` огорожен. Чтобы повторить
демонстрацию с начала, пересоздаём пару из резервной копии:

```bash
docker compose exec backup sh /scripts/backup.sh
docker compose down
docker volume rm vidsec_video-db-data vidsec_video-db-standby-data
docker compose up -d
# подождать ≈30 с, пока standby скопирует данные
docker compose exec backup sh /scripts/restore.sh latest
```

## Ограничения

- Репликация асинхронная: при падении primary могут потеряться последние транзакции, которые
  не успели дойти до standby (на практике доли секунды). Синхронная репликация убрала бы потерю,
  но при падении standby остановила бы запись.
- Старый primary не возвращается в строй автоматически: его нужно пересоздать как новый standby.
- Для репликации используется учётная запись владельца БД. В промышленной системе нужен отдельный
  пользователь только с правом REPLICATION.
- Redis, хранилище S3, nginx и api работают в одном экземпляре, их защищает только автоперезапуск.
- Всё работает на одном хосте. Следующий шаг: развести узлы по разным машинам (Kubernetes или
  Docker Swarm) и вынести резервные копии на отдельное хранилище.
